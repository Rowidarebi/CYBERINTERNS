## 2. How to read the requests

**Priority**

| Priority | Meaning | Needed by |
|---|---|---|
| **P1** | Expires, changes when someone acts, or decides today's containment | Today. Before anyone changes the host, the credential or the firewall. |
| **P2** | Decides scope and severity, and does not expire in the next day | Within 48 hours (Wednesday 21 October) |
| **P3** | Narrows a hypothesis. Only worth doing once P1 and P2 are moving. | This week (Friday 23 October) |

**The table in Section 3** has one row per request. Rows run P1 first, in the order in which the evidence is lost or changed, then P2, then P3. The request ID is in bold at the start of the Artefact Requested cell. All times are UTC. Windows include a buffer: at least 20 minutes before the first event and at least an hour after the last, unless the request is a look-back. **Possible Conclusion if Obtained** gives both outcomes: what it means if the evidence is there and what it means if it is not. **Why Needed** ends with a **Loss risk** sentence that says whether the evidence may already have been lost.

**"If it is absent, it means"** uses the same six classes as the report (Section 19). They are different failures with different fixes: **never existed**, **not enabled**, **not forwarded**, **aged out**, **not supplied**, **third party**.

**Owners** are our best reading of `04-Stakeholders.md`. You may not own most of these systems. Where ownership is not documented we say **ownership to be confirmed**. We are asking you to route, not to do everything yourself.

**Handling for every request**

- Copy, never move. Hash with SHA-256 before and after the copy. Record the hashes.
- Write-once storage that is not on the system being examined. Named recipient only.
- Keep a custody log (template in Section 7).
- No credentials, keys or customer data in tickets, chat, email or the pull request.
- Failed-login lines can contain a password typed into a username field. Treat the log files as sensitive.

4. **Host evidence** (ER-23) goes with ER-01 to ER-03, before any rebuild.
5. **Production audit** (ER-24) **and the Azure Firewall queries** (ER-25) can run in parallel. Both read retained data.

**How these map to the report.** Section 19 of the report uses six classes. **Never existed** and **Not enabled** become *never existed*. **Not forwarded** becomes *existed, not collected*. **Aged out** stays *may have aged out*. **Not supplied** and **Third party** become *not yet obtained*.

**Why the difference matters here.**

- The first and third classes leave "cannot rule out" open for good. The second and fourth can close it, and they deserve the effort now.
- Only some of the third class has a date on it: Sunday 25 October 04:11 for UAT restores, a day at a time for the oldest host log lines and Azure Firewall rows, and the moment of rotation for the credential's metadata, which is overwritten and not aged.
- Most of this list is in the second and fourth classes. That is good news: it means most of what we need is already somewhere.

**Limits that remain even if every request is met**

1. Nothing here shows what happened before the oldest retained record on each surface. The credential may be older than any log, so the exposure window can be longer than anything we can check.
2. An empty audit result excludes use only if the action groups that would have recorded it were on.
3. Complete host, firewall, database and storage evidence still cannot rule out a copy of the credential held somewhere we have not looked (I7-C8).
4. A restore shows state, not reads. Only Query Store or an audit record shows a read.
